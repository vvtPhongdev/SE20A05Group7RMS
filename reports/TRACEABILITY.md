## Cross-document rules

1. REP-02 owns requirement meaning and business rules.
2. REP-03 owns implementation design and data access.
3. REP-01 owns delivery status and workstream ownership.
4. REP-04 owns unresolved gaps and release risks.
5. REP-05 owns installation and user-facing operation.
6. If a route changes, update `screens.md`, this matrix, REP-01 and REP-05 together.
7. If a workflow state changes, update the state-machine PUML, REP-02, REP-03 and this matrix together.
8. If a Prisma model changes, update the class PUML, REP-03 and affected rows in this matrix.

## Known terminology reconciliations

| Older term                                           | Current term                   | Resolution                                                                                                                                                                         |
| ---------------------------------------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HR_MANAGER`, `HR_RECRUITER`                         | `HR_LEADER`                    | Current shared enum and UI use one HR role.                                                                                                                                        |
| `CvDocument`                                         | `CandidateCV`                  | Current Prisma model is `CandidateCV`; database table is `candidate_cvs`.                                                                                                          |
| 13-state lifecycle                                   | Extended implemented lifecycle | Current enum retains compatibility and operational states such as `REVISION_NEEDED`, `PLAN_APPROVED`, `SCREENING`, `INTERVIEW_COMPLETED`, offer states, `CLOSED`, and `CANCELLED`. |
| Automatic offer after Admin hire vs HR-created offer | Both supported                 | Admin decision can atomically create a sent offer; `OfferLetterService` also supports explicit generate/review/send.                                                               |
